# Security review

Audit date: 27 October 2026. This is a source review plus the listed backend and isolated-browser regressions. It is not a formal penetration test, production configuration review, or third-party security scan. No third-party target was scanned. Secrets, tokens, passwords and private payloads are intentionally excluded from this report.

## Assessment

No critical or high-severity application-layer authorization bypass was demonstrated in the tests run. The workspace boundary, role checks, secret encryption/redaction, cloud destination checks, local companion origin/token boundary, report expiry/revocation and admin restrictions have direct source and automated-test evidence. Public production security is **not ready to approve** because network egress enforcement, HTTPS/reverse proxy behavior, real provider configuration, worker monitoring and production recovery controls were not exercised on a deployment host.

## Controls reviewed

| Control | Evidence reviewed | Assessment |
| --- | --- | --- |
| Authentication and session handling | Laravel Sanctum/API middleware, Next gateway, account recovery and session tests; browser security settings | HttpOnly/SameSite cookie-based gateway design is present. Production Secure-cookie/proxy forwarding must still be checked behind the real HTTPS proxy. |
| CSRF and origin | `apps/web/src/app/api/gateway/[...path]/route.ts` validates the configured origin for mutations; browser test rejects a cross-origin mutation | Application-level origin check and SameSite protection are tested. Reverse-proxy-origin handling is not verified on a live deployment. |
| Workspace isolation and RBAC | `WorkspaceAccess` and resource query scoping; viewer, cross-workspace foreign-key and resource tests | Server-side workspace checks are present and covered. Registration cannot grant platform admin. |
| Last-owner and invitation security | `WorkspaceController` blocks removal/demotion of an owner; invitation tokens are hashed, identity-bound, expiring, revocable and one-time | Backend tests explicitly reject owner removal/demotion, role escalation, identity mismatch and token reuse. |
| Admin authorization | `AdminController` authorization checks plus workspace/user/quota tests | Non-admin reads and quota changes are denied; quota changes are audited. Browser paths verify admin and non-admin states. |
| Cloud SSRF controls | `SafeTarget`, `CurlTransport`, approved-host review workflow, special IPv4/IPv6 cases, redirects/proxies disabled, pinned address plus TLS hostname validation | Application-layer controls are strong in the reviewed code and tests. They do not replace deployment egress filtering. |
| Local companion | `scripts/companion.mjs` loopback bind, random session token, constant-time token compare, exact Origin/Host, DNS checks, explicit localhost flag, 1MiB body/response cap, timeout, four concurrent executions and cancellation | 3 local fixture tests pass. Browser receives a live local response by design; this is an opt-in developer capability, not a server-side secret vault. |
| Environment secrets | Encrypted database casts/storage; API omits secret values; `null` preserves an unchanged secret; switching secret to public requires a replacement | Backend and browser tests confirm persistence, masking and preservation. Never print or decrypt secrets in support/debug output. |
| Run/result redaction | Server redacts known secret values and sensitive JSON keys/headers; query values are removed from stored URLs; Local results redact sensitive fields before record submission | Redaction tests cover JSON, headers, URLs, assertions and exports. Arbitrary free-form credential strings cannot be inferred reliably in every raw text body. |
| Audit integrity/export | Scoped detail/export queries return safe columns; export is capped at 500 records | Backend tests verify workspace scope, detail fields and bounded export. Append-only semantics are implemented for recorded audit events; this audit did not attempt database-owner tampering. |
| Report links | Random share token stored as a SHA-256 hash, one-time display, expiry/revocation checked on every read, fixed read-only snapshot fields | Backend and browser tests verify expiry/revocation/scope and no sensitive request payloads. |
| File/body bounds | RequestRules and executor bounds; companion request/response caps; response truncation fails explicitly | Code and tests confirm limits. Semantic multipart-form construction was not exhaustively exercised. |
| Rate limits, quotas and retention | Separate API/execution throttles, workspace daily quota lock, run pruning/cascade | Backend regression tests verify separate counters, quota behavior and retained-data deletion policy. Production queue/retention scheduling still needs operational verification. |
| Logging | Sensitive delivery errors and executor errors are designed to expose codes rather than credentials; encrypted local outbox | Source/test evidence is targeted. Full reverse-proxy, process and cloud-provider log review is not possible without deployment logs. |

## Findings and release implications

| ID | Severity | Finding | Evidence / impact | Action |
| --- | --- | --- | --- | --- |
| SEC-01 | High, production blocker | Host-level executor egress enforcement is unverified. | Application DNS/IP pinning and exact host allow rules are tested, but Docker is unavailable on this host and `infrastructure/executor-firewall.sh` was not applied. Compose network separation alone does not restrict outbound destinations. | Apply the firewall or an equivalent egress gateway on the real host. Confirm blocked internal/metadata/loopback targets and an approved HTTPS destination from inside the executor. Recheck after restart/recreation. |
| SEC-02 | High, production blocker | HTTPS reverse-proxy and production cookie/origin behavior have not been validated. | Deployment files and exact-origin checks exist, but no TLS certificate, public origin or proxy was configured in this audit. | Verify TLS, forwarded headers, Secure/HttpOnly/SameSite cookies, exact origin mutation rejection, health routing and proxy request/body limits on a staging host. |
| SEC-03 | Medium | Secret redaction cannot guarantee detection of arbitrary credentials placed in raw free text. | The implementation redacts known environment values and sensitive keys; unstructured content may not identify a credential without a matching value/key. | Keep credentials in encrypted environment variables and references; avoid embedding them in arbitrary raw URL/body text. Add format-specific tests as new response types are introduced. |
| SEC-04 | Medium | Local mode necessarily exposes the response and temporary entered values to the signed-in browser process. | The companion sends a local target response to the browser, where local result redaction occurs before the authenticated history record is written. | Preserve explicit pairing, origin checks, localhost opt-in, short-lived pairing state and clear user-facing mode indication. Do not describe Local mode as protecting against a compromised browser. |
| SEC-05 | Medium | Full auth-mode/body-mode request coverage is incomplete. | Existing tests cover local HTTP methods/raw bytes/headers and cloud Basic auth templating, but not every API-key, query, multipart and error combination. | Complete the controlled-local-fixture matrix in `FUNCTIONAL_QA.md` before treating all Postman-style modes as independently validated. |
| SEC-06 | Medium | Provider-side email/webhook success and operational retries are not verified against real services. | Unit tests use encrypted local outbox and fake webhook transport; no SMTP/webhook provider credentials were configured. | Test non-production provider credentials, rejection/timeout/retry, redaction and delivery-status semantics before enabling production notifications. |
| SEC-07 | Medium | Worker and scheduler liveness are not instrumented/verified. | Admin Console intentionally displays `Not monitored`; application counters do not prove worker health. | Add a real worker heartbeat and scheduler/queue-age alert path. Keep the UI honest until telemetry exists. |

No application data, existing E2E databases, backups, `.env` file or Laravel APP_KEY was rewritten by this audit. Each E2E run used a random separate application key and a fresh database/user verified by the harness; those test databases were retained. The audit did not snapshot/hash every existing development database record, so this is a no-write integrity confirmation rather than a full record-by-record comparison.

## Residual authorization and network tests

Automated regressions cover cross-workspace reads and relationships, viewer restrictions, last-owner protection, admin-only data and quota operations, report token expiry/revocation, audit export scope, local companion Origin/Host/token checks and private-address rejection. These tests were non-destructive and used SQLite, isolated MySQL E2E data, or ephemeral loopback fixtures. No arbitrary internal network addresses were probed from a real executor and no external service scan was performed.
